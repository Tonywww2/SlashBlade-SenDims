# 客户端启动耗时调查

当前版本从 JVM 启动到可用主菜单实测 **116.479 秒**。近期两次未启用 JFR 的记录分别为 **120.163 秒、132.062 秒**，说明目前启动大约需要两分钟，同时存在明显波动。值得优先处理的是 Mixin 操作码查询的重复反射、拔刀剑 OBJ 解析，以及普通模型准备与烘焙。

本轮完成调查和设计，没有启用新优化、修改正式 Java 功能或更换模组版本。采样通过 Prism 命令行启动，到主菜单后自动正常退出，未进入任何存档。

## 测量口径与启动阶段

调查日期为 2026 年 10 月 15 日。环境为 Minecraft 1.20.1、Forge 47.4.10、GraalVM 21.0.5、i7-13700K（24 个逻辑处理器），正式 mods 目录有 358 个 JAR，合计约 1.12 GiB。JVM 保持 Xms 6 GiB、Xmx 12 GiB、SoftMaxHeap 10 GiB、非分代 ZGC 和 Graal 编译器；现有渲染优化、动态光源和 Brute Force 配置保持原样。

首次主菜单时间由探针读取 RuntimeMXBean 启动时间并检查 TitleScreen、加载覆盖层消失得到；再观察 40 tick 后退出，这段约 2.36 秒的等待不计入启动时间。ModernFix 同轮报告 116.693 秒，计时基准相差约 0.21 秒。JFR 从 JVM 启动时开启，执行采样周期 10 毫秒，只用于热点定位；不能把本次与历史记录的差值当作优化收益。

| 顺序区间 | 本次耗时 | 含义 |
| --- | ---: | --- |
| JVM 启动到 ModLauncher 开始 | 8.138 秒 | Prism ForgeWrapper、缓存文件校验、早期库加载 |
| ModLauncher 到 Preloading Tricks 就绪 | 12.011 秒 | 早期加载器、JAR 文件系统与引导插件等 |
| Preloading Tricks 就绪到内嵌依赖汇总 | 10.293 秒 | 模组发现、元数据和 JarInJar 扫描 |
| 内嵌依赖汇总到原版 bootstrap 开始 | 18.218 秒 | 模块图解析、类加载与转换等 |
| bootstrap 开始到 Forge 初始化标记 | 10.902 秒 | 原版初始化、客户端类加载和 Mixin 等 |
| Forge 初始化标记到资源重载开始 | 29.802 秒 | 模组构造、注册、客户端初始化等 |
| 资源重载开始到可用主菜单 | 27.115 秒 | 模型、纹理、语言及各资源监听器 |
| **合计** | **116.479 秒** | 顺序区间相加，未重复累计并行工作 |

区间名称对应可观察日志标记，不代表该区间只执行一种任务。例如，第一批模组构造早于 Forge 的日志标记，不能把 29.802 秒全部归因于 Forge 本身。

历史未采样记录：最近两次平均 126.113 秒，范围 120.163～132.062 秒；另有早期版本和参数状态下的 82.258 秒记录，单独保留作线索，不纳入当前基线平均值。本次 JFR 的 JVM CPU 占整机平均约 14.6%，整机平均约 41.9%，外部负载和串行阶段都可能影响结果。目前没有足够证据把历史波动归因于某一次模组更新或某项渲染优化。

## 已定位的具体消耗

主菜单前共得到 3,455 条 Java 执行样本。下述调用树比例包含子调用，可能互相重叠；它们不是总启动时间的百分比，也不能直接换算为可节省秒数。分配量来自 JFR ObjectAllocationSample 的加权估计，表示累计对象周转，不是常驻内存。

### Mixin 操作码名称反复扫描反射字段

调用链为 `MixinPreProcessorStandard.transform → Bytecode.getOpcodeName → Class.getDeclaredFields → Class.copyFields`。已核对实际使用的 Mixin 0.8.5 字节码：预处理遍历指令时查询操作码名称，查询过程每次都读取 `Opcodes` 的字段列表，再寻找对应整数。这用于构造转换活动上下文，关闭普通日志并不会绕过该调用。

`Bytecode.getOpcodeName` 出现在 **140 条执行样本**中，相关调用树的分配权重约 **6.76 GiB**；其中 `Class.copyFields` 是主要来源。该路径同时出现在 Render thread、模组加载线程和 bootstrap 线程，且可能处于类转换的锁内。当前 Mixin Booster JAR 未提供针对这一方法的实现，运行采样也确认重复反射仍存在。

设计：在引导阶段建立只读、有界的操作码名称表，保留字段顺序、起始标记、最小值、未知值及异常回退的原语义。普通 Forge 模组构造时才初始化已经太晚，需要先设计与现有 ModLauncher／引导层的适配，不直接用常规模组 Mixin 去改写 Mixin 自身。未来用独立的早期配置开关控制，失败时沿用原路径。这是启动优化的首要候选，实际秒数收益尚未测量。

### 拔刀剑 OBJ 预加载中的正则与字符串分配

调用链为 `ModelResourceLoader.loadResources → BladeModelManager.getModel → WavefrontObject.loadObjModel`。OBJ 解析样本分布在启动后 **89.967～98.978 秒**，由一个 Lightspeed 工作线程执行，共 **465 条样本**，约占全部执行样本的 **13.5%**。该调用树的分配权重约 **5.43 GiB**。

实际字节码中，每行会调用 `String.replaceAll` 整理空白；顶点、法线、UV 和面还会经过多次正则校验、substring 和 split。主菜单前，整个启动过程的累计分配权重约 66.21 GiB，因此这部分解析确实有降低对象周转的空间。

模组 JAR 内 `assets/*/model/*.obj` 共发现 **131 个条目，解压后约 65.83 MiB**，这是磁盘资产清单，不等同于最终资源优先级合并后的加载数量。最大两个文件是 Lethal Slash Project 的 `dissociator.obj`（8.46 MiB）和 `light_sword.obj`（7.93 MiB）；特供模组的 `mizushi.obj` 约 2.72 MiB。无需删模型，也能先优化解析器。

设计第一步：使用一次扫描的空白及数字分词，减少正则 Matcher、重复验证和 token 数组；保持面顺序、法线、UV 翻转、组名、错误行号和异常行为，未知语法回退。用现有 131 个资产加人工边界样例做解析结果对照，再考虑后续缓存。当前 P2 的 OBJ 优化针对每帧提交与 Face 数学临时量，**没有覆盖启动解析**。

设计第二步：若仍有明显消耗，再考虑按资源内容、资源包优先级和解析器版本缓存中间结果；缓存须有体积上限，重载必须失效，不能共享可变渲染状态或把旧模型带入新资源包。

OBJ 任务与普通模型准备并行。约 9 秒是样本覆盖区间，不是独占主线程 9 秒；即使把这项任务加速一半，也不能据此承诺总启动减少 4.5 秒。

### 普通模型准备、烘焙与资源尾段

资源重载区间有 2,245 条执行样本，其中模型相关调用树命中 **1,323 条，约 58.9%**。`ModelBakery` 准备和解析在约第 90～99 秒活跃，`ModelBakerImpl.bake` 的采样区间为 **99.775～105.390 秒**，之后仍有模型映射、BlockModelShaper 缓存和资源应用。模型准备与烘焙主要集中在同一个工作线程，属于更值得追踪的资源关键路径。

设计：优先研究不可变模型输入、变体解析和依赖扫描的重复工作与缓存命中情况；允许按资源代次、内容及加载器版本失效。未审计的模组自定义模型、可变几何及带渲染副作用的烘焙保持原流程，不直接全局并行化。

纹理透明像素处理也有 193 条执行样本，但主要集中在约第 90～92 秒并已分散到多个线程；YACL GIF／WebP 解码有 170 条样本，集中在约第 90.5～92.5 秒。这两类工作较早完成，对总耗时的影响需要结合关键路径判断。可后续探索未打开的配置预览图片按需解码，保留任务 HUD 图片、动画和 GL 资源生命周期，不通过降低画质换启动速度。

### 早期 JAR 文件系统及模块解析

前约 30.4 秒包含明显的 JAR 文件系统初始化工作。NativeMethodSample 中有 **502 条**命中 `WindowsNativeDispatcher.GetVolumePathName0`，上层为 `ZipFileSystem` 初始化时的可写性检查，再上层是 `UnionFileSystem.openFileSystem`。Java 执行样本另有 **244 条**命中模块解析 `java.lang.module.Resolver`。

设计：先审计同一路径是否被重复打开、重复枚举，尽量复用已有索引和只读文件系统生命周期；若需要加载器适配，再按文件身份和版本严格失效。不能从 native 样本数量直接推出它占了多少秒，也不能凭此判断是某个模组、磁盘或防护软件的问题。本轮没有修改 Forge 库、签名校验或启动器组件。

## 当前配置的真实状态

| 项目 | 核实结果 | 处理建议 |
| --- | --- | --- |
| ModernFix 常规启动优化 | class search cache、dynamic DFU、registry validation、texture stitching 等已在默认启用列表 | 不重复添加同类优化 |
| ModernFix KubeJS／faster ingredients | 用户覆盖为 false | 保留兼容设置，不能仅凭名称重新开启 |
| Lightspeed common 配置 | 资源索引预加载、专用重载池、资源查找和存在性缓存为 true | 先核对具体路径命中率 |
| `lightspeed-client.toml` | 当前 JAR 只注册 COMMON 配置；不存在旧 client 配置类和并行烘焙等字段 | 这是遗留文件，改其中开关不会得到预期效果；本轮保留原文件 |
| Lightspeed 工作池 | 当前代码读取 `-Dlightspeed.workers`，默认 `max(2,min(32,CPU-2))`，本机为 22；缓存池默认 2 | 旧 TOML 的 `parallelismLevel` 不是有效控制项 |
| Lightspeed 资源快照 | 本次 shaderHits=137；model／native／font 的 hit、miss 均为 0 | 0 次访问不能解释为缓存命中或失败，需检查对应路径是否覆盖当前调用 |
| Smooth Boot | main=27、bootstrap=1，多数后台线程优先级为 1 | 线程数值得纳入后续对照，但不能断言减少线程一定更快 |
| Lightspeed bootstrap agent | 自动安装为 false | 不为此次调查写入机器专用 Agent 路径；需先评估与现有引导插件的兼容和分发方式 |

之前从遗留 `lightspeed-client.toml` 推测“黑名单导致并行烘焙停用”的判断已撤回：这些字段不属于当前运行版本。当前 JAR 和采样才是本轮结论的依据。

## 优先级与验证计划

这里的优先级仅针对启动优化，均处于设计阶段。

| 优先级 | 工作 | 预期作用与验收条件 |
| --- | --- | --- |
| P0 | 操作码名称表与早期引导适配 | 消除重复反射；与原方法逐值对照，验证所有重载和未知值回退；单独配置开关 |
| P0 | SlashBlade OBJ 解析器减少分配 | 逐模型对比顶点、UV、面及组顺序；完整错误和兼容回退；独立开关，不与每帧提交开关混用 |
| P1 | 普通模型输入和变体解析缓存 | 优先覆盖关键路径中的不可变输入，记录命中率；资源包、模组或加载器变化必须失效 |
| P1 | JAR 文件系统和目录索引重复工作审计 | 先证明有重复再缓存，验证路径优先级及文件关闭；加载器改动另行评估 |
| P1 | 统一启动线程预算 | 用实际有效配置协调 Smooth Boot 与 Lightspeed，观察阶段时间、CPU 和锁等待；保留 Graal 与当前 GC 配置 |
| P2 | YACL 配置预览图片按需解码 | 只有证明影响关键路径后实施，检查首次打开界面及资源重载行为 |

目前能确认的是消耗位置，不能提供已经实现的加速百分比。操作码查询和 OBJ 调用树合计命中的分配权重约 12.20 GiB，但其中并非全部可以消除，也不是能从峰值堆里扣除 12.20 GiB。下一轮整体实现完成后，再分别测任务耗时、启动总耗时和分配量。

验证时固定模组 SHA、JVM、资源包和缓存状态，以 JVM 到可用主菜单作为主指标；至少取 3 次相同口径结果报告中位数和范围，首次缓存构建单列。资源重载、存档加载和首次 JEI 就绪独立计时，不将并行工作时间相加。每个代码优化都有独立开关，先做离线语义对照，最后统一实机验证。

## 不作为本轮主要加速目标的部分

本次 KubeJS startup 脚本 1.355 秒、client 脚本 0.570 秒，合计约 1.925 秒。暂不为节省这部分时间重写整套脚本。特供模组注册代码只在 1 条执行样本中出现，未成为主要 CPU 热点；其模型资源仍计入 OBJ 调查。

主菜单探针稳定时记录 23 轮 ZGC。首次主菜单之前的 67 个暂停事件累计约 **1.58 毫秒**，最长约 **0.12 毫秒**；并发回收过程约 20 秒的累计耗时不能当作停顿。主菜单稳定时堆使用约 5.14 GiB，主菜单前分配周转的优化价值主要是降低 CPU、带宽及 GC 工作，而非消除几十秒暂停。

存档加载后的 JEI 是另一项问题。已有日志中 `Starting JEI` 为 51.59 秒，其中 `Registering Runtime: jei:forge_gui` 计时 38.18 秒；该计时可能包含向渲染线程发布或等待，不能认定为插件独占 CPU 38 秒。这发生在进入存档后，不包含在主菜单启动耗时中，本轮没有重新进入存档测试。

本轮未测试或修改光影参数，也未把 dynamicShape、VoxelShapeComponents 或遮挡剔除纳入启动实现计划。

## 清理状态

启动参数及配置已恢复，正式模组和原存档保持不变。

原始采样、截图、临时日志、测试备份及一次性探针工具已按用户要求清理；本报告保留实现说明与测试结论。
