### 内存与动态光源

Prism `instance.cfg` 已设置最小堆 6 GiB、最大堆 12 GiB、`-XX:SoftMaxHeapSize=10G`，移除 `AlwaysPreTouch`。保留非分代 ZGC，并显式设置 `-XX:-ZGenerational`。本机 GraalVM 21.0.5 的离线启动标志核验显示，分代 ZGC 会将 `EnableJVMCI` 和 `UseJVMCICompiler` 关闭，因此未启用它。首轮最终功能联调的运行时标志确认 Graal 编译器仍开启、预触碰关闭，堆初始／最大／软目标分别为 6／12／10 GiB。

6 GiB 是最小堆，10 GiB 是软目标，12 GiB 仍是可增长的硬上限；不能据此直接声称平均省 2 GiB，或 GC 次数一定减少。本轮短功能复核没有形成新的配对内存／GC 统计。

`config/sodiumdynamiclights-client.toml` 已设 `self=false`，原 `entities=false`、`block_entities=true` 与 SLOW 刷新模式保留。Lucent 的玩家、实体与掉落物光源及 `lightRefreshRate=40` 保持原值。仅移除 SDL 重复的玩家手持来源，没有删除光照效果来换取帧数。没有实施 SDL 形状查询早退，也不改动 Integrated Dynamics 的配置。

### 代码设计与配置开关

所有新功能均有独立开关，默认并实际启用。配置文件：`config/slashblade_sendims.toml`。关闭开关即走原上游路径；配置加载／重载时发布选项快照，热顶点循环不查询 Forge 配置映射。

| 配置键 | 实现 |
| --- | --- |
| `performance.rendering.draconicGrinderGeometry` | 磨粉机剑模型几何缓存与统一提交 |
| `performance.rendering.grinderCacheMiB` | 几何数组预算，当前 2 MiB；0 强制回退，范围 0–16 |
| `performance.rendering.slashbladeObjSubmission` | SlashBlade Face 数学临时对象复用 |
| `performance.hud.minimapIconFilters` | 小地图图标重复纹理过滤状态写入去重 |
| `performance.hud.questBackgroundBatching` | UIQuest 背景渐变切片批量提交 |
| `performance.hud.questTrimmedTextCache` | UIQuest 不可变裁剪文本缓存 |
| `performance.buffers.immediatelyFastFixedBufferViews` | ImmediatelyFast 固定缓冲单元素集合视图复用 |

**Draconic：**缓存由渲染器持有，记录原始剑模型及四方向、左右两侧的八种静止姿态；动画起点和终点的零位姿均可命中。缓存数组总负载受 2 MiB 预算约束，不为每台机器建立一份。动画中只合成一次变换，再写入原 `VertexConsumer` 和原共享批缓冲，避免 CCL 每顶点的操作流水线。保留实时位置、法线、纹理、光照、overlay 和 Iris 扩展属性生成。不建立独立 GPU 缓冲或跨方块实例化队列，也不承诺新增 draw-call 合并收益。模型、资源代次或预算变化会失效；未知模型／格式／顶点接收器／额外属性回退原实现。

**SlashBlade：**每线程复用一个法线矩阵与向量，法线矩阵由每顶点构造改为每个面准备一次，默认 alpha 省去 `Vector4f` 和装箱回调。读取实时面顶点、法线、UV 操作、颜色与光照；保留 `RenderOverrideEvent`、渲染类型、发光层与 glint。自定义 alpha、Face 子类或重入时回退。没有缓存可变刀状态，也不改变模型覆盖事件。

**小地图：**在一次 FTB HUD 绘制范围内，只跳过相邻同一纹理的重复 min/mag 过滤写入，不改变图标顺序或透明合成。外部 GL 参数写入、纹理切换、新帧和退出作用域都会使备忘失效，不跨帧假设 GL 状态。

**任务 HUD：**原有 60 个背景切片仍按原顺序、顶点和颜色绘制，改为在边框／文字前统一刷新；任务状态、数量与进度每帧读取。文本缓存固定 128 槽，以内容、裁剪宽度、字体对象和资源代次区分；超长文本不保留，碰撞直接替换。资源重载和退出世界时清理。

**缓冲：**仅复用 ImmediatelyFast 已有固定缓冲的不可变单元素 Set 视图，最多 64 槽。保留 fallback 动态缓冲路径、刷新顺序和原 native buffer 生命周期；资源代次变化、关闭优化和 BufferSource.close 后释放引用。不另建本地缓冲池。

## 内存与分配

Java 堆始终承诺 12 GiB。有效测量中的 GC 后堆用量范围约 5.57–7.73 GiB；ZGC 并发收集后的用量并不等于精确保留对象体积。有效窗口最大 GC 暂停为 0.134 ms，遥测中的累计 GC 时间包含并发工作，不能直接解释为卡顿暂停。

| 300 生物 | 444.4 | 2.735 |
| 混合工厂 | 304.5 | 1.900 |
| 工厂战斗 | 375.4 | 3.721 |
| Draconic | 190.0 | 2.419 |

水晶向量是 Draconic 的突出分配项，而磨粉机剑模型是突出 CPU 路径，两者需要分别处理。ImmediatelyFast 的缓冲函数承担上游 HUD／绘图请求，仅凭此分配栈不能认定该模组净收益为负；应继续追踪 RenderType 创建、批次提前刷新和缓冲复用，保持显示内容等价。

额外核对 JFR 中 37 个 ZAllocationStall 事件：均未与有效的 20 秒测量窗口相交，其中渲染线程 9 次、最长约 1.44 秒，发生在场景切换／导出等窗口外阶段。这与 GC 全局暂停不同，且包含测试工具导出等负载，不能直接当作日常游戏卡顿；瞬态分配余量仍需验证。不能只根据 GC 后堆用量就降低最大堆；ZGC 需要为并发收集期间的分配留下余量。[Oracle ZGC 调优说明](https://docs.oracle.com/en/java/javase/11/gctuning/z-garbage-collector4.html)。

没有凭采样分配量认定内存泄漏。

Windows 工作集计数中位数约 39.3 GiB，甚至高于整机物理内存。这与当前非分代 ZGC 的多重映射账目一致，不能当作唯一物理 RAM 用量，也不能简单除以三。私有提交中位数约 6.76 GiB，系统可用物理内存最低约 2.16 GiB；这些口径不能混加，系统可用内存还受其他进程影响。[ZGC 架构说明](https://dev.java/learn/jvm/tool/garbage-collection/zgc-deepdive/)、[Windows 内存计数定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)

测量结束后的对象直方图统计约 4.99 GiB 对象体积；这是诊断 GC 后的快照，可能清理软缓存，不能直接作为日常堆需求。

直方图中的数组、HashMap 和 String 占比较高；单独的 BlockState、ModelResourceLocation、BakedQuad 对象分别约 117、84、75 MiB，尚未计算它们引用的对象。类直方图不能按模组准确归属共享数组／集合，也不能证明泄漏。后续应将资源模型缓存的保留关系与长期进出世界后的增长一并核对；本轮未保存完整堆转储。

## 本轮离线复核与收益评估（2026-10-14）

本节根据优化前的 68 场景资料作离线机会评估；不代表本轮实现后的内存、GC 或 FPS 实测。Brute Force Culling Revived 2.2.3 由用户随后添加，旧基线不包含它。本轮实现和末尾功能复核见报告前面的实施状态。

Integrated Dynamics 的 `core.general.cacheCableModels=true` 与 `machine.general.disableCableCollision=true` 已开启，配置保持原值。

### dynamicShape 已排除

按用户最新要求，`dynamicShape`、VoxelShapeComponents 改写及 SDL 形状查询早退均退出本轮实施与后续收益预算；不改变 `machine.cable.dynamicShape=true`。此前的形状调用链属于历史评估，不计作可兑现收益。

### 内存收益的量化边界

| 指标 | 现有有效窗口 |
| --- | --- |
| 堆用量最低／逐秒平均／最高 | 5.68／9.03／11.82 GiB |
| GC 后堆最低／均值／最高 | 5.57／6.62／7.73 GiB |
| 堆承诺量最低／平均／最高 | 12／12／12 GiB |
| ZGC 周期开始数／每分钟 | 138／6.09 |
| 每个约 20 秒窗口 GC 次数最低／平均／最高 | 0／2.03／6 |
| 全线程加权分配估计 | 458.2 MiB/s |

GC 数量以有效窗口内开始的完整 ZGC 周期定义，不用 398 个暂停阶段当成 398 次收集；跨窗口结束造成它与 130 条窗口内 After GC 记录数量不同。GC 周期包含并发工作，不是停顿时间。

有效窗口的 GC 暂停阶段共 398 个，总计 6.416 ms、平均 0.016 ms、最高 0.134 ms。稳态全局暂停本身不是主要帧数瓶颈；减少分配的价值主要在分配／并发收集开销和瞬态余量，不能由此承诺巨大的 FPS 提升。

已定位的水晶、透明排序和 CCL 变换临时对象（已排除全部形状路径）约占全线程分配权重的 3.1%；缓冲与 ModernUI 文本路径另占 21.2%，后一组仍需查上游及可复用程度。分母包含没有非 JDK 栈归因的样本，不能只把已归因栈作为总分配。已开启的模型缓存和 P0/P1 不重复计入新收益。

下面用三组明确假设评估更广范围的剩余机会（水晶与排序并未在本轮实现，32 MiB 是原机会模型假设，并非本轮 2 MiB 几何缓存的实际内存成本）：保守只削减前一组 25%；中间削减前一组 50%、缓冲／文本 25%；积极削减前一组 75%、缓冲／文本 50%。它们是条件模型，尚不是实现后的预测置信区间，实际收益可以为零；缓存和 FPS 上升也可能增加常驻堆或每秒分配量。

| 机会模型，非实测 | 全线程分配量减少 | 固定收集时序：堆最低／平均／最高 GiB | 固定触发阈值：同等时长 GC 周期 |
| --- | --- | --- | --- |
| 保守假设 | 0.8% | 5.71／9.04／11.81 | 137（6.04/分钟） |
| 中间假设 | 6.9% | 5.71／8.89／11.49 | 129（5.67/分钟） |
| 积极假设 | 12.9% | 5.71／8.75／11.18 | 120（5.30/分钟） |

堆列假设原收集时序不变、保留集合不变，以 GC 后均值 6.62 GiB 为预算代理，把其上的短命部分按分配降幅缩放，并加上 32 MiB 的新缓存预算。最低值略升是缓存代价，不能承诺所有内存指标都下降。GC 列则假设收集触发阈值和算法不变，按 N×(1−r) 估计次数。**这两列是两种不同响应情形，不能把堆下降和 GC 次数下降同时当成已经能达到的收益。**若 ZGC 选择更少收集，堆最高值可能仍接近原值；Xms=Xmx 不变时，承诺量依旧 12 GiB，逻辑上限也依旧 12 GiB。

上述次数还要求帧率预算保持不变。Render thread 占分配权重约 74.5%，解锁帧率下更多帧会抵消分配优化；若渲染每帧分配减少 15% 而 FPS 提高 20%，这部分每秒分配反而约为原先的 1.02 倍。不能因此承诺实际 GC 一定减少。

本轮已启用 Xms=6 GiB、Xmx=12 GiB、SoftMaxHeapSize=10G 并移除 AlwaysPreTouch。较小 Xms 配合 ZGC 归还能减少空闲时承诺量，但稳态最小／平均／最高值与真实物理 RAM 节约目前不可可靠计算。仅作为算术示例：将空闲承诺从 12 降至 10 GiB，逻辑承诺减少 2 GiB；10 GiB 只是软目标，当前没有长时间内存对照证明承诺量会稳定在此值。Xms=Xmx 会禁用堆归还，且预触碰影响启动驻留；改变它们涉及延迟权衡。[Oracle ZGC 说明](https://docs.oracle.com/en/java/javase/15/gctuning/z-garbage-collector.html)

资源模型保留关系没有完整堆转储证据，不能再叠加一个任意“常驻内存节省百分比”。本机 GraalVM 21.0.5 的分代 ZGC 会关闭 JVMCI／Graal 编译器，已通过离线 JVM 标志检查确认，因此保持非分代 ZGC，并显式设置 -XX:-ZGenerational。当前 Windows 工作集计数存在 ZGC 多重映射，不能把逻辑堆减少量直接换算成物理 RAM。

### 动态光源收益

优先保留 Lucent 的玩家、燃烧／发光实体及掉落物光源，把 SDL 的重复玩家来源关掉，保留其方块实体功能。旧“仅 Lucent”组关闭了 SDL 的整个动态模式，而不是只关闭 self；它是已启用 SDL self=false 方案的近似参照，不能视作该精确方案的性能收益已经得到验证。

| 负载 | 原双开两次 FPS | 仅 Lucent 对照 FPS | 相对两次基线的差值 | 帧时节约 ms |
| --- | --- | --- | --- | --- |
| 普通，只手持火把 | 525.6／542.6 | 541.6 | -0.2%～+3.0% | -0.003～+0.056 |
| 普通，大量燃烧／发光生物与掉落火把 | 204.4／214.1 | 231.3 | +8.0%～+13.2% | +0.346～+0.569 |
| 固定光影，只手持火把 | 324.5／327.2 | 317.2 | -3.0%～-2.3% | -0.096～-0.071 |
| 固定光影，大量燃烧／发光生物与掉落火把 | 141.7／144.2 | 151.2 | +4.9%～+6.7% | +0.323～+0.442 |

仅手持光源没有稳定的正收益证据；保留 Lucent 的光影手持组甚至略慢。密集发光环境有较明确的优化空间：普通约 +8%～13%、固定光影约 +5%～7% 的既有对照差值，对应约 0.32～0.57 ms/帧。已启用方案尚无配对性能实测，稳妥的工程预期应包含零收益，不能将该百分比推广到全整包。只去重玩家来源对无光源工厂几乎无直接收益，本轮没有实现形状查询早退，其收益完全排除。

如果关闭 Lucent 的实体／掉落物光源，旧“仅 SDL”组会更快，但 SDL 当前 entities=false，场景效果不等价，不能把该差值计作保留光效的优化。两套光源全关的密集组对照约为普通 +12%～17%、光影 +12%～14%，同样属于删去光源效果的参考，不能当成等价优化收益或严格理论上限。没有真实游玩各类场景的时间占比，无法推导整包的平均提升；采样顺序／缓存波动也尚未被多轮 ABAB 消除。

Lucent 的 `lightRefreshRate=40` 单位是次/秒，对应最多约 25 ms 一次；先前计划中的“40→60／80 ms”表述错误。若下一轮需要刷新预算探索，应按 40→30／20 次/秒理解；本轮未修改，现有数据也没有这一项的收益。所有光影包画质参数调优永久退出计划。
